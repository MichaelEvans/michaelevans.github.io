Testing Android Backup and Restore With AndroidX

Getting a new phone is exciting. You take it out of the box, peel off the protective film, and sign in. Your apps begin downloading, your wallpaper shows up, and before long it looks like your phone again.

You open an app. Sign in. Open another one. Sign in again. What was the password for this one? Now you’re digging through your password manager and waiting for verification codes.

Even after you’re signed in, things aren’t quite right. Your settings are back to their defaults. The book you were reading has forgotten your page. The draft you hadn’t finished is gone. The app made it to your new phone, but it doesn’t feel like your app anymore.

Google is pushing developers to fix this. Its August app quality announcement says that starting in April 2027, apps with sign-in will need to support restoring sign-in with the Restore Credentials API to keep Play Store visibility.

Getting the user signed back in is one half of the problem. Getting their data back is the other half, and in my experience it’s the half that quietly breaks. Someone adds a new preferences file and forgets to update the backup rules. An installation ID gets copied to a new device, and now two phones look like the same install. Data encrypted with an Android Keystore key gets restored onto a device that doesn’t have that key, and the app crashes on first launch. None of these show up in a normal unit test.

Fortunately, AndroidX now has a backup testing library that lets us automate the whole round trip. Let’s take a look.

Testing it the old way

Before this library, testing backup meant running a few adb commands by hand, roughly following the backup testing guide:

Then you’d open the app and poke around to see whether your data came back. That works, but it’s manual, it’s easy to forget, and “poke around” isn’t a great assertion. It’s the kind of check that gets done once when backup is first set up and never again.

How the library works

The library splits the test into two halves:

  • backup-host runs on your development machine (or CI) and drives the whole process over ADB: run some code in the app, trigger a backup, wipe the app’s data, restore it, run more code.
  • backup runs inside the app on the device. This is where you write data before the backup and check it afterwards.

Why split things up? Clearing app data kills the process that would normally be running your instrumentation test. Keeping the orchestration on your computer lets the test keep going across that wipe and pick back up inside the restored app.

Android decides what gets backed up, based on your app’s backup rules. The library doesn’t fake any of that; it just gives you a way to test the rules you’ve written.

Version note: This post uses 1.0.0-alpha01, released September 23, 2026. It’s an early alpha, so expect some of this to change. Check the release notes if you’re on a newer version.

Decide what should come back

Before writing any test code, it’s worth writing down what should survive a restore. It’s tempting to check that everything comes back and call it a day, but restoring the wrong thing is a bug too.

For this post, let’s use a reading app that lets you take notes:

  • Should come back: the current book and page, plus the user’s notes.
  • Should stay behind: an installation ID that’s generated fresh on each install.

When you do this for your own app, a few things almost always belong in the “stay behind” list:

  • Installation IDs, push tokens, and other per-device identifiers
  • Anything encrypted with a Keystore key, since Keystore keys don’t move to the new device
  • Auth tokens, which should go through Restore Credentials instead of a file backup
  • Caches that can just be rebuilt

  • Seeded proves the installation ID existed. Otherwise the “it didn’t come back” check would pass even if we never wrote it.
  • Cleared proves the wipe worked, so whatever we see afterwards really came from the restore.
  • Restored is the one we care about.

If your app generates a new installation ID on startup, change the cleared and restored checks to assert that the ID isn’t "old-installation", rather than that it’s missing.

  • BackupRestoreExtension injects the BackupRestoreController, and its APIs are suspending, which is why everything is wrapped in runBlocking.
  • The little action() helper checks every result. When a check() throws on the device, the host gets back a failure result, not an exception, so if you forget to check the result your test will pass no matter what happened on the device.

Once it passes, break it on purpose. A test you’ve never seen fail hasn’t proven much yet.

  1. Add <exclude domain="sharedpref" path="reading_progress.xml" /> to the cloud-backup rules, rebuild, reinstall, and rerun. The book/page check should fail after restore.
  2. Put that back, then remove the device_state.xml exclusion. Now the installation ID check should fail.
  3. Restore the original rules.

If both of those fail the way you’d expect, you can trust the test to catch the regressions you actually care about.

Other transport modes

The test above uses CLOUD_ENCRYPTED, but you can swap in CLOUD_UNENCRYPTED or DEVICE_TO_DEVICE to test the other paths. There’s also LOCAL, which is handy as a quick smoke test, but the archive it gives you isn’t a real portable backup.

It’s worth being clear about what these modes don’t do: they simulate the backup policies, but they don’t send anything to a real Google account or a real second phone.

Running in CI

A couple of tips if you want to run this in CI:

  • Run backup tests one at a time per device. Backup configuration is shared device state, so parallel runs will trip over each other.
  • Put a timeout on the whole CI job. The library has its own timeout settings, but it’s an alpha, and I wouldn’t rely on them alone to keep a hung device from eating your build minutes.

Wrap-up

Backup is one of those features that’s easy to forget about, because nothing tells you it’s broken. You usually find out from a one-star review written by someone who just got a new phone.

I wouldn’t try to cover every file in your app on day one. I’d pick the one or two things your users would be most annoyed to lose (their place in a book, their notes, their settings) and the one or two things that should never follow them (installation IDs, anything tied to the Keystore), and write a test for those. Once that’s in place, adding a check is a few lines every time someone adds a new preferences file.

Combined with Restore Credentials for sign-in, that gets you a lot closer to an app that just picks up where the user left off. Hopefully it saves a few of your users an evening of setting things up again!
