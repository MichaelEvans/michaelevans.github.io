How to Combine PagingData With Other Flows Using asItemSnapshotListFlow

If you’ve ever tried to combine a Flow<PagingData<T>> with another Flow, you’ve probably discovered that PagingData doesn’t behave like a regular list of items.

That’s by design. PagingData is meant to be consumed by Paging’s presenters, like PagingDataAdapter or LazyPagingItems. Those presenters know how to listen for page events, trigger more loads as the user scrolls, and update the UI as new items arrive.

But sometimes your screen needs the currently loaded items as state. Maybe you want to combine them with selected IDs, optimistic likes, or locally edited titles. This has been a common source of confusion for developers trying to combine PagingData with another Flow, expose paging from an MVI-style screen (one where the UI renders a single state object), or update loaded items without forcing a full refresh.

Paging 3.5.0 adds a new API for this: asItemSnapshotListFlow.

The new shape: loaded items as state

Each emission gives you the currently loaded items in snapshot.items, along with counts of any placeholders before and after them. You can read and transform that list anywhere you collect the flow.

One heads-up before we go further: reading from a snapshot doesn’t tell Paging to load more, and append() and prepend() are the only way to do it with this API. If you render these items yourself, you’ll need to call them. We’ll get to that in Loading more data.

It’s a good fit for UI-only state: selection, muted rows, expanded or collapsed sections, local filters. None of that belongs in your database or network model. It’s just how this screen reads the loaded items.

Optimistic likes and local display edits

When a user taps a like button, you want the UI to update right away, even while the network request is still running. The same goes for editing a display title locally before saving.

Historically, Paging pushed you toward updating the backing data source and invalidating the PagingSource. That’s still the right answer for durable data. But for a temporary visual change, going through a full paging refresh is a lot of ceremony for a heart icon.

These overlays don’t replace your source of truth. If the request succeeds, you still need to update your backing data source, and once the refreshed item comes back with the new value you can drop the override so it can’t mask a later change from the server. If the request fails, drop it right away, as setLiked does above.

The payoff is that your UI doesn’t wait on Paging to show a local change.

The 3.5.0 release notes also list Pager.refresh() and Pager.retry() for recovering from load errors when you work from snapshots.

Wrap-up

For a straightforward paged list, I’d still reach for collectAsLazyPagingItems() or PagingDataAdapter, since they handle scroll-driven loading for you.

I’d use asItemSnapshotListFlow when the screen needs local edits, filters from another Flow, or lookups across the loaded items. You get a list you can work with using the Flow operators you already know.

It does come with a couple of tradeoffs. Every emission gives you the whole loaded list, so any overlay change re-maps all of it, which is worth keeping in mind for very large lists. And you’re responsible for loading more pages when you render snapshots yourself.
